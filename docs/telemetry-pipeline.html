Race Telemetry Pipeline

How one GPS fix travels from a boat's rover unit, over radio, through the base station's event detection, into RegattaUp's webhook and entities, and back out to the race map — with every wire format and record shape along the way.

Repos race-tracker · regatta-up Transport LoRa radio / UDP (sim) → HTTPS webhook Store Redis (live) + Base44 entities (durable)

End-to-end overview

Five hops turn a raw GPS fix into a scored lap on the race map. The rover only ever knows its own position and whatever course marks the base last told it; the base is the one place position data, event detection, and the RegattaUp connection all meet.

📡
Two independent loops. Position frames flow rover→base continuously at up to SIM_GPS_HZ; course marks flow base→rover on a slow heartbeat (MARKS_BROADCAST_INTERVAL_MS, 60s default) plus on-demand whenever they change. Neither loop blocks the other — a rover that's never heard marks still transmits its own position.
§1

Rover

boatAgent.js

One process per boat — src/boatAgent.js, GPS source is either real hardware (ubxParser.js) or simGps.js under SIMULATE=1.

Every fix is logged locally regardless of radio conditions; only fixes that clear TX_DISTANCE_M since the last transmitted one are actually sent — a stopped boat doesn't re-key the channel every tick.

Radio protocol

protocol.js

Three fixed-length frame types share one channel, told apart by a leading sync byte before either side needs to know how many bytes to expect. Every frame ends in a mod-256 checksum over its own body.

"Ping fleet" admin action — asks every boat to report right now, ignoring the movement gate. No per-boat payload; each boat replies with an ordinary position frame after its own random jitter.

Base station

baseStation.js

Every decoded frame fans out to five independent consumers — recording position never waits on event detection, and a RegattaUp outage never blocks the live track.

FinishLineWatcher

One instance per boat, keyed by boatId. Compares each new fix's segment against committeeFinish↔finish using orientation tests — reports a lap only on a genuine upwind crossing, independent of the simulator's own lap count.

OnGridWatcher

Is this boat behind the pin↔committeeStart line, within onGridZoneM? Re-fires ongrid on every qualifying fix; offgrid once on exit.

MarkRoundingWatcher

One per boat per gate (windward/leeward × green/black). Fires when a boat crosses the virtual gate extending markRoundingExtensionM beyond a mark.

FoulWatcher new

One instance per boat. Watches the same three segments as the start/finish line complex — pin↔committeeStart, committeeStart↔committeeFinish, committeeFinish↔finish — and reports a foul whenever a boat crosses the start or finish line downwind (the wrong direction — a legitimate start/finish only ever crosses upwind, same convention FinishLineWatcher already uses) or passes between the two committee marks in either direction at all.

Webhook queues → RegattaUp

*WebhookQueue.js

Four SQLite-backed queues (lap / on-grid / mark-rounding / foul) share one paced send loop — a burst of events (a whole fleet going on-grid at once) never fires that many concurrent requests. Every attempt is recorded for backoff; a row is only removed once RegattaUp actually accepts it.

sequenceDiagram
  participant W as Watcher
  participant Q as SQLite queue
  participant H as mylapsWebhook
  participant R as Racer / Race
  participant E as LapCompletion /
MarkRounding

  W->>Q: enqueue(event)
  loop every postIntervalMs (500ms)
    Q->>H: POST { mode, decoded: { tranCode, rtcTime, strength } }
    H->>R: match tranCode in class_entries
    alt race + racer found
      H->>E: create record
      H-->>Q: 200 OK
      Q->>Q: remove row
    else no match / error
      H-->>Q: non-200
      Q->>Q: recordAttempt(), retry with backoff (max 5m)
    end
  end

⏱
rtcTime is microseconds. The lap's own GPS-derived crossing time, converted from the watcher's millisecond timestamp (crossingTime * 1000) — not when the webhook happened to fire.
🔗
mode is always explicit. All four event types send mode and decoded.strength - none of race-tracker's own payloads distinguish an event type by a field's absence. The receiver still treats a missing mode as 'lap', since this same endpoint also accepts hits from real MyLaps decoder hardware, which has no concept of mode at all.
🚧
foul is race-tracker-side only, for now. reason is a free-form string — "downwind start line", "through committee gap", or "downwind finish line" today (see foulWatcher.js), more later. mylapsWebhook doesn't branch on mode: "foul" yet — see §5's mode diagram, still lap/ongrid/offgrid/mark only — an explicit unrecognized mode falls into its own catch-all branch (skipReason: "unknown mode: foul", no LapCompletion/entity side effect, just the unconditional MyLapsTag log). That's a safe no-op today, not the intended handling — a Foul entity + mode branch is being built separately, directly on the RegattaUp platform.

RegattaUp — mylapsWebhook

base44/functions

Frontend read path

RaceMap3D.jsx

The map never talks to the base station directly — it polls two read-only functions that go straight to Redis for anything live (positions, marks, the on-grid polygon) and to entities for anything scored (laps, mark roundings, regatta metadata).
